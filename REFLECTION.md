# Reflection

Working on the Expense Tracker in stages taught me that Codex is most useful when I give it a clear scope and review its plan before it changes files. We started with project rules and reusable skills, then moved through the data model, validation, JSON storage, services, the command-line interface, and documentation. That order helped me understand how each part depended on the previous one. I also learned to be specific about decisions such as storing money as integer paise, including both ends of a date range, and preserving an expense ID when editing it.

The approval workflow worked well for keeping the work understandable and controlled. I could check the proposed files and behavior before implementation, then review the resulting code and test output. The skills gave Codex a repeatable process, especially the rule to inspect the existing project and wait for approval before implementing a feature. Seeing the service tests use temporary directories also made the storage tests safer and easier to reason about.

The process did not work perfectly every time. The launch scope first named `main.py`, but I recognized that running the package with `python -m expense_tracker` also required `__main__.py` to call the CLI. The first service test set also missed invalid and impossible dates at both filter boundaries, so I asked for additional tests without changing the service implementation. The Python launcher was unavailable in the working environment too, which meant I had to distinguish the documented Windows command from commands actually verified there. These moments showed me why generated code and test claims need to be checked rather than accepted at face value.

The most useful rule for me was to inspect, propose, and get approval before implementation. In another AI-assisted project, I would define acceptance criteria and file scope even more carefully at the start, and make sure I reserve time to review edge cases and run checks in the same environment the intended users will use. Codex helped with implementation, but I remained responsible for deciding what the program should do and checking that the result matched those decisions.
